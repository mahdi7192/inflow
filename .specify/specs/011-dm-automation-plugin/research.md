# Architectural Research & Decisions: Direct Message (DM) Automation Plugin

**Feature**: `011-dm-automation-plugin`  
**Date**: 2026-10-20  
**Status**: Completed & Approved

---

## 1. Plugin Architecture & Canonical Workspace Routing

### Context
inFlow is evolving from a single comment-reply tool into a multi-plugin control plane. The first plugin manages post/reel comments. The second plugin manages Instagram Direct Messages (DMs). Routing must be deterministic, prevent hydration flashes, and cleanly organize account workspaces.

### Decision
- **Root Route (`/`)**:
  - Unauthenticated requests redirect to `/login`.
  - Authenticated users with assigned accounts automatically redirect to their default active account's primary plugin workspace (`/@{username}`).
  - Authenticated users without assigned accounts show the clean `EmptyTenancyView`.
- **Workspace Scoped Routes**:
  - `/@{username}` (or `/@{username}/comments`): Comment Automation Plugin (reels, posts, triggers, comment logs).
  - `/@{username}/dms`: Direct Message (DM) Automation Plugin (master toggle, triggers, AI prompt, web context, MCP tools, DM logs).
- **Sidebar Navigation**:
  - Features two dedicated plugin navigation items:
    1. **اتوماسیون کامنت** (`MessageSquareQuote` / `LayoutGrid`)
    2. **اتوماسیون دایرکت** (`Send` / `Bot`) with real-time active/inactive status pill.

### Alternatives Considered
- *Tab-based state without URL routing*: Rejected because it breaks browser back/forward history, deep linking, and violates Constitution Principle XII (Canonical @username URL Scoping).
- *Subdomains per plugin*: Unnecessary complexity for a unified single-origin control plane.

## 2. Instant Master Toggle & Auto-Save UX

### Context
Users expect seamless, low-friction control over automation. Having to click "Save Changes" after flipping an enable/disable switch introduces confusion and potential forgotten saves.

### Decision
- The Master Automation Toggle (`enabled`: 0 or 1) uses an **optimistic UI update** coupled with an immediate background `POST` / `PATCH` to `/api/accounts/{username}/dm-automation`.
- A lightweight, non-blocking toast notification (`sonner` or shadcn toast) confirms the transition instantly (e.g. `اتوماسیون دایرکت با موفقیت فعال شد` / `اتوماسیون دایرکت متوقف شد`).
- Form inputs (prompts, keywords, URLs) retain an explicit "ذخیره تنظیمات" (Save Configuration) button with dirty-state indicator to prevent accidental drafts from overwriting production rules prematurely.

## 3. Dual-Layer AI Trigger & Reply Pipeline

### Context
Not all incoming DMs should be replied to, and replies need not always be generated by LLMs. Users need fine-grained control over what triggers a response and how that response is composed.

### Decision
A two-layer pipeline is established:

```text
[Incoming DM]
     │
     ▼
[Layer 1: Trigger Matching]
 ├── Mode 'all' ───────────► PASS to Layer 2
 ├── Mode 'keywords' ──────► Does text contain keywords? ── Yes ──► PASS to Layer 2
 │                                                        └── No  ──► SKIP & Log
 └── Mode 'ai_context' ────► Semantic Intent Evaluation ── Yes ──► PASS to Layer 2
                             (Prompt condition, e.g.     └── No  ──► SKIP & Log
                              "سؤال درباره قیمت یا سایز")
     │
     ▼
[Layer 2: Reply Mode Resolution]
 ├── Mode 'direct' ────────► Send static predefined template
 └── Mode 'ai' ────────────► Ingest Context (Prompt + URLs + MCPs + Story text)
                             ──► Query LLM
                             ──► Send dynamic response
```

### Rationale
- Decouples *filtering* from *generation*.
- Saves LLM tokens and API cost by rejecting irrelevant messages at Layer 1.
- Allows static templates for simple greetings or coupon codes while using LLMs for complex advisory.

## 4. Rapid Web Context Extraction

### Context
Online shop owners want the AI to answer using their live website (product pages, FAQ, shipping policies). However, traditional browser scraping or heavy headless engines (CDP) introduce high latency (5-10s) and excessive resource usage.

### Decision
- Dedicated high-speed HTTP reader tool in the worker plane:
  - Fetches the raw HTML via lightweight HTTP client (`curl_cffi` / `httpx` or Node `fetch`).
  - Strips scripts, styles, navigation bars, and footer boilerplate using a clean readability text extractor.
  - Caches extracted markdown/plain text in an in-memory TTL cache (default 15 minutes) keyed by URL hash.
  - Extracted text is compressed into concise markdown chunks before injection into the LLM system prompt.
- Time budget: Target < 1.5 seconds for uncached fetches; < 50ms for cached reads.

## 5. Model Context Protocol (MCP) Integration

### Context
For structured data (e.g. inventory queries, live order tracking, customer loyalty points), static web scraping is insufficient. inFlow already has Back-Office MCP bindings and token management.

### Decision
- The DM automation configuration exposes an **MCP Knowledge Source** selector in the UI.
- Superadmins/Tenants can toggle available MCP server bindings (e.g. `maghzook` for shop catalog, `soodup` for financial/crm, or custom local MCP servers).
- During AI resolution, the worker agent exposes only read-only query tools from enabled MCP servers to the model.
- The UI provides clear hints and placeholder syntax (e.g., `<mcp:tool_name>`) guiding the user on how to instruct the AI to call tools when needed.

## 6. Follow-Gating & Verification Flow

### Context
Creators use DM automation to convert casual viewers into followers. The comment plugin has a post-level `dm_require_follow` setting. The DM plugin requires its own independent account-level follow-gating rule.

### Decision
- When `require_follow = 1` in DM automation:
  - When an incoming message arrives, the worker checks whether the sender is a follower of the target account.
  - **If NOT following**:
    1. Sends the configured `follow_prompt_text` (e.g., `سلام! برای دریافت پاسخ و مشاوره کامل، لطفاً ابتدا پیج را فالو کنید 🙏`).
    2. Logs the interaction in `dm_logs` with status `pending_follow`.
    3. Halts further automated replies on this message.
  - **If following**:
    1. Immediately proceeds with standard trigger evaluation and response.
  - **Re-verification on subsequent messages**:
    1. When a user with previous `pending_follow` logs sends a new message (e.g. "فالو کردم" or repeating the question), the worker re-checks follower status.
    2. Once confirmed, their status transitions to active and the pending/new query is answered normally.

## 7. Story Reply Ingestion Architecture

### Context
Stories are uploaded frequently and expire in 24 hours. Users cannot foresee every story's exact visual content when creating general automation rules in the control plane.

### Decision
- Decouple a heavy standalone Story Plugin from v1.
- In the DM Automation flow:
  1. **Direct Reply Mode**: Incoming story replies are matched against standard keywords or answered via the default static text.
  2. **AI Reply Mode**: When an incoming DM is a story reaction/reply, the worker agent captures the referenced story text/caption and attaches it to the AI prompt context as `[Story Context: ...]`.
  3. The LLM combines the story reference, the user's incoming message, and configured knowledge sources to craft a relevant answer.
  4. If the story has expired or has no text/sticker content, the model gracefully handles the message as a general inquiry.

## 8. Absolute Idempotency & Polling Integration

### Context
Instagram DM webhooks or polling loops may receive redundant events or trigger concurrent runs. In accordance with Constitution Principle III, double-replying on Instagram is strictly unacceptable.

### Decision
- `dm_logs` table features a `UNIQUE` constraint on `message_id`.
- The background agent uses an atomic lock check:
  - Before executing LLM generation or sending a DM, it inserts an idempotency lock row with `reply_status = 'locked'`.
  - If a duplicate `message_id` arrives, SQLite rejects the insert (`SQLITE_CONSTRAINT_UNIQUE`) and the agent aborts.
- `GET /api/agent/poll?account={username}` is enhanced:
  - Returns `dm_automation: { enabled, trigger_type, trigger_context, trigger_keywords, reply_mode, direct_reply_text, ai_prompt_instructions, web_context_urls, mcp_servers_config, require_follow, follow_prompt_text }`.
  - Returns `processed_dm_ids: string[]` (recent 200 message IDs) for zero-latency client-side skipping.
- `POST /api/accounts/{username}/dm-logs` records execution outcomes and unlocks/completes records.
